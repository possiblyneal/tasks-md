# apps/tasks

## Purpose

One Go binary with three modes. Bare `tasks` prints usage, `tasks <verb>` acts and exits, and `tasks api` serves the JSON `apps/web` reads and the compiled client's files beside it. `docs/adrs/0003-replace-the-tui-with-a-browser-client.md` records why the person's surface is a browser client this binary serves; `docs/adrs/0004-tasks-md-is-the-store.md` records why the store is a `TASKS.md` file in each Repo rather than a database.

It reads through `list`, `repos`, `lint`, `stats` and `GET /api/state`, and writes through `add`, `capture`, `edit`, `move`, `delete`, `tags rename` and `repeat` and their routes. The pass brings a file up to today before any of them reads or writes it. `docs/adrs/0005-tasks-md-keeps-its-own-history.md` records why every write is a commit in a tasks history of its own.

## Ownership

- `src/cmd/tasks/` — `package main`, nothing but the call into `cli`. It sits under `cmd/` because `scripts/package` names the artifact after the main package's import path.
- `src/cli/` — mode dispatch and the verbs. `ModeOf` decides which mode an invocation asked for; `Run` takes its streams as arguments so every mode is testable without a process.
- `src/taskfile/` — the `TASKS.md` format: `Parse` reads a file into its Task tree plus every problem by line, `Write` gives the tree back as canonical text, and `Version` hashes one tree's. It reads no disk.
- `src/repos/` — the config file and Repo discovery: `ConfigPath`, `Load`, `Find`, and `FileName` and `Holds`, the one spelling of the store's file every package uses.
- `src/board/` — the one read of every Repo: discover, parse each file afresh, work out Blocked and each Task's parents, and keep what a `Narrowing` asks for; `Weekly` counts the metrics. Every verb and route reads through it.
- `src/write/` — the one write path onto a Repo's TASKS.md: `Add`, `AddSubtasks`, `EditTask`, `Move`, `Delete`, `RenameTag`, `Repeat`, `SeriesOf` (a rule and its next dates), `HistoryOf` (a Task's history, read and never written) and `Pass`, and every rule they answer to. The CLI's verbs and the API's routes both call it. `broker.go` is what the Broker is shown (`DumpOf`, `Briefs`, `BriefOf`: Repos and Tags by name, no ids) and what it said made writable (`FromCapture`, `FromProposal`, `NamedIn`). Its errors are what the exit statuses and status codes are mapped from: `Refused`, `Invalid`, `NoTask`.
- `src/history/` — a Repo's tasks history: `Write` takes the lock, readies `.tasks.git`, commits a hand edit first, commits the change and pushes; `Flags` is what a Repo is marked with; `MainCheckout` is where a linked worktree's writes go; `Log` and `Show` read the history back. It is the only package that runs git, and it never reads inside the file.
- `src/api/` — `tasks api`: routing, JSON encoding, the status an error takes, the client's files, and the midnight pass. `GET /api/files` is the one route holding a rule of its own.
- `src/schedule/` — Scheduling's rule arithmetic: parsing a recurrence rule, writing it back, and the dates it produces. `write` is its one caller.
- `src/ai/` — the Broker client: an OpenAI-compatible HTTP call out to `inference-runtime-broker`. `tasks capture` and the Broker routes are its callers; it reads nothing on disk and writes nothing.
- `assets/starter.md` — the `TASKS.md` a new Repo starts with: `# Tasks`, `color:` and the one comment telling Agents to use `tasks`. `possiblyneal/template` ships a copy of it as `TASKS.md` in its payload, beside `/TASKS.md` and `/.tasks.git` in the payload's `.gitignore`; nothing in this binary writes it, since there is no `tasks init`.
- `deploy/systemd/` — `tasks-api.service`, the `systemd --user` unit that starts `tasks api` on boot. `.unit.json` declares `ships: executable`.

## Local Contracts

- **A verb and a request make the same in-process call.** `tasks list` and `GET /api/state` both call `board.Discover` then `board.Read` with a `board.Narrowing`, so a person and an Agent are answered by one read. A rule enforced in a handler is one an Agent at a terminal never gets.
- **Roots come from `~/.config/tasks/config`** (`$XDG_CONFIG_HOME/tasks/config` when set), a plain key file read with the standard library: one `root = <path>` a line, `#` comments and blank lines ignored, `~` expanded to the home directory, a path that is neither absolute nor under `~` refused. `name = <actor>` is the one other key. Any other is an error naming the line. No file, or no `root` line, means one root, `~/code`.
- **Every write is one commit in the Repo's tasks history.** `.tasks.git` beside TASKS.md is a git-dir whose worktree is the Repo folder, created on the first write with branch `tasks`; it commits TASKS.md alone with hooks skipped, as `chore(tasks): <verb> ^<id> …` with a `Generated-By: <Actor>` trailer, authored by the host's git user. A hand edit found before a write is committed first as `chore(tasks): commit a direct edit` with `Generated-By: direct edit`. Where the folder is a git repo, `/TASKS.md` and `/.tasks.git` are appended to its `.gitignore` unless something already ignores them.
- **A write is pushed to branch `tasks` on the code repo's origin, and a failed push fails nothing.** The commit stays, the Repo is flagged `not pushed` until a later write's push goes through, and a folder with no origin is `not backed up`. Nothing merges that branch.
- **A Repo in a mess refuses writes, exit 3 and `409`.** Conflict markers in TASKS.md, or a tasks history mid-merge, mid-rebase or on a detached HEAD. So does a file holding a line a rewrite would drop. A person clears it by hand.
- **A Repo's flags are on every read.** `flags` on each Repo in `GET /api/state` and `tasks list -json`, the FLAGS column of `tasks repos` (`-` for none), and a warning on stderr after a write that left any. They are worked out afresh from git each time and are part of the ETag.
- **A Repo made from the template is ready for its first write.** `cli/template_test.go` holds `assets/starter.md` to `tasks lint` clean, to a first `add` keeping its preamble, and to the template's ignore entries being the ones a write looks for, so the write leaves `.gitignore` and the code history untouched. A change to the starter or to those entries is a change to the template's copy too.
- **Writes to one Repo run one at a time.** `history.Write` holds an exclusive `flock` on the Repo folder across read, change, commit and push; the folder rather than the file, because the file is replaced by a rename.
- **A write acts on the nearest TASKS.md at or above the working directory, or the Repo `-repo` names.** From inside a linked git worktree, that search starts from the same path in the main checkout. The API names the Repo in the body's `repo`.
- **The Actor is `TASKS_ACTOR`, else the config's `name`, else the login name.** `tasks api` resolves it once when it starts.
- **`add` puts a top-level Task above the ended ones,** in Inbox unless `-state` says otherwise, `-until` only while Deferred and `-attach` repeated, with a fresh id of four `[a-z0-9]` and `created:` today. A fresh id is one the Repo has never held: not in the file and never added by a commit in its tasks history, so a deleted Task's id is not handed to another and its history is not drawn on the new one. Every attribute is checked before anything is written.
- **`move` is refused, exit 3 and `409`, for a parent and for a Task already in Doing.** Doing is how a Task is taken. On every move the checkbox follows the State; `ended:` is written when a Task ends and cleared when it reopens, and the Task sinks below its open siblings or rises back above the ended ones; a parent its move ended or reopened does the same. `reason:` is held only while Deferred or Declined and `until:` only while Deferred, so leaving either clears them. `-until` (`until` over the API) dates a move to Deferred and is refused on any other State; a move without it leaves no `until:`. A move to the State a Task is in commits nothing.
- **A Repo is a folder directly inside a root that holds a `TASKS.md`.** Only direct children are looked at, so a nested clone, a worktree or a `tmp/` inside a Repo is never one. Dot folders are skipped. Links are followed, and two paths to one real folder are one Repo. One folder name under two roots is a config error naming both paths, and the first is kept.
- **The Repos are rescanned and every file re-read on each request.** Nothing is cached between calls, so a new Repo or a pull shows without a restart.
- **A config error never hides the Repos that were found.** `tasks list` prints the read and then the error, exiting 1; `GET /api/state` answers `200` with the sentences in `errors`.
- **The format is #97 and #105's.** A preamble (`# Tasks`, `color: <name>`, a comment), then title lines `- [ ] <title> | <state> #tags`, each followed in order by `- id:` (four of `[a-z0-9]`) and `- created:`, then any other `- label: value` lines (unknown labels kept, in order), a blank line, and the description. A Subtask is indented two spaces a level, five levels at most.
- **The checkbox wins over the word.** `[x]` is Done and `[-]` is Declined whatever the word says; `[ ]` under an ended word is Backlog.
- **A parent's State is worked out from its Subtasks.** While any is open it is the first of Doing, Backlog, Inbox and Deferred among them; once all have ended it is Declined if every one was, otherwise Done. A parent line saying otherwise is a problem on that line, and the read carries the worked-out State.
- **Blocked is any same-Repo blocker that has not ended.** `- blocked by: <id>, <id>` names Tasks in the same file; a blocker naming no Task is a lint problem and blocks nothing.
- **Lint is `taskfile.Parse`'s problems and nothing else.** Parse errors, duplicate ids, unknown blockers, a missing or out-of-order `id`/`created`, an id of the wrong form, a parent line disagreeing with its Subtasks, and conflict markers, each by line. A write gives a disagreeing parent line back as it was written rather than correcting it, so the hand edit stays flagged until a person fixes the line; the State worked out is still the one that counts. `tasks lint [file...]` prints `file:line: message` and exits 1 on any; with no files it lints every Repo found. The read carries the same list as each Repo's `problems`, so a broken Repo is flagged where it is drawn rather than hidden.
- **One wire shape for `tasks list -json` and `GET /api/state`.** `board.Of` builds it: `{"repos": [{name, path, color, tasks, problems, flags}], "errors": [], "sorts": [...], "today": "YYYY-MM-DD", "metrics": [{start, added, done, declined}]}`; a Task is flat, each Task before its Subtasks, carrying `id, title, state, tags, created, attrs, description, line, depth, parent, parents, leaf, blocked, rank, version`, with `parents` the titles above it, outermost first. An empty collection is `[]`, never `null`.
- **A narrowing is the same seven things on both surfaces.** `-repo`/`repo`, `-state`/`state` and `-tag`/`tag` repeated (any of them), `-search`/`search` (case-insensitive over id, title and description), `-unblocked`/`unblocked=true` (Blocked Tasks out), `-blocked`/`blocked=true` (Blocked Tasks alone), `-sort`/`sort`. A State or a sort there is not, or Blocked both in and out, is refused through `Narrowing.Check`.
- **The metrics are twelve weeks of Added, Done and Declined, read from the files.** `board.Weekly` counts, oldest first, each week starting on a host-local Monday and the last holding today: a Task's `created:` is Added, its `ended:` is Done or Declined by the State that counts. Every Task counts, parents included, and a parent's end is the latest of its Subtasks' and never its own `ended:` line. Nothing reads git, so a deleted Task is in no week. They follow a Narrowing's Repo and Tags alone, kept as a read keeps them, so a Tag on a parent counts the parent and not its Subtasks; search, States, Blocked and sort do not narrow them. Today comes from `cli.now` and `api.Options.Now`.
- **`tasks stats` is the lane counts and the metrics in the terminal.** `-repo` and `-tag` (repeated) narrow both as the board's chips do; the lanes count leaf Tasks per State, the cards the board would draw. An unknown Repo is exit 1, an argument exit 2.
- **A sort orders siblings and never flattens the tree.** `board.Sorts` is the one list (`file title deadline created priority estimate`), and the read serves it as `sorts`. Priority ranks high, med, low and estimate S, M, L; a Task missing the key sorts last; ties keep file order. `rank` is each Task's place across every Repo (sort key, then Repo, then file), so a surface drawing several Repos in one lane orders by it.
- **`GET /api/state`'s ETag hashes the host's date, every Repo's name, path, file mtime and size, flags, the config errors and the query.** The date is there because `today` is in the body, so past midnight the same files are a different response. A different view or a changed file is never answered `304` for another. A bad query and an unknown Repo are refused before the ETag is looked at, so `If-None-Match: *` cannot be told nothing changed about a view it can never be shown. The tag goes only on a `200`. `api.matches` reads `If-None-Match` as RFC 9110 writes it.
- **The API's status codes are the CLI's exit statuses.** `200` for done (`201` with `{"id"}` for `POST /api/tasks`), `400` for usage (exit 2, including a body field the route does not know), `404` for a Repo or Task that is not there (exit 1), `409` for a refusal (exit 3), `500` for a failure (exit 1), with the body `{"error": "<the sentence the CLI would print>"}`. `api.fail` and `cli.failed` are the two places that mapping is written.
- **Six write routes.** `POST /api/tasks` takes `write.New`'s fields plus `repo`; `POST /api/tasks/{id}` takes `write.Edit`'s plus `repo`; `POST /api/tasks/{id}/move` takes `{repo, state, reason?, until?}`; `POST /api/tasks/{id}/delete` takes `{repo, version?}`; each answers `{"id"}`. `POST /api/tasks/{id}/subtasks` takes `{repo, version?, subtasks: [write.New]}` and writes them all under the Task as one commit (`add ^a ^b under ^id`), an ended Task reopening and rising as a move's parent does, answering `201` with `{"ids"}`. `POST /api/tags/rename` takes `{from, to, versions?}` over every Repo and answers `{"repos": [names written]}`.
- **A write naming a version is refused, exit 3 and `409`, when that Task's tree has changed.** `version` is the first 12 hex of the sha256 of the top-level tree's canonical text, carried on every Task in the read, a Subtask carrying its tree's. An edit to another tree in the same file goes through. It is optional: a one-shot `tasks edit` without `-version` leans on the lock alone. `move` takes none.
- **`edit` changes only the attributes it names.** An empty value takes one off; `-tag` and `-blocked-by` (repeated) replace the whole set; `-attach` and `-detach` add and take off `attachment:` lines. Labels it does not name, unknown ones included, stay where they are. State is not an attribute here: `move` holds its rules. Every value is checked as `add` checks it, against the Task's State, and a Task cannot block itself.
- **`delete` takes the block and its Subtasks out.** The parents above it are settled as a move settles them, and its ids are struck from every other Task's `blocked by:`. The tasks history keeps the block.
- **`tags` counts every Tag across every Repo; `tags rename <from> <to>` is one commit per Repo carrying it.** A Repo without the Tag is not written. Every Repo is checked before any is written, so a stale tree refuses the whole rename; a Task carrying both keeps one.
- **Every write fills a hand-typed Task's missing `id:` and `created:`,** a fresh id and today, after the version check, and dates a hand-ticked end with `ended:` today. `repeat` and a pass that commits are writes too.
- **A Series is a `- series:` attribute, written in `schedule.String`'s form.** `tasks repeat <id> <rule…>` sets it, `-off` takes it off, and either prints the rule and its next five dates from today; with no rule it prints them and writes nothing. `GET /api/tasks/{id}/series?repo=<name>` answers `{rule, dates}`, `{"rule":"","dates":[]}` for a Task with none; no `repo` is `400`.
- **A Task's history is read from `.tasks.git`, newest first.** `GET /api/tasks/{id}/history?repo=<name>` answers `{"entries": [{at, actor, subject}]}`: every commit whose subject names `^<id>`, and every direct edit that changed the Task's own lines (its title line up to the next Task's, compared as written, so a Subtask's lines are its own), the subject without `chore(tasks): ` and `at` the author date in the host's zone. A direct edit's `actor` is `""`, unknown. A hand edit shows once a write has committed it; the read commits nothing. The file as it stood before the first write is that first direct edit, so it is on every Task already in it. No history yet is `{"entries":[]}`; a Task not in the file is `404`, no `repo` `400`. There is no verb: `log --grep` on the tasks history answers it at a terminal.
- **The pass runs before every verb and request, over the Repos it reads or writes.** `list` and `GET /api/state` over the narrowed Repos, `repos` and a bare `lint` over all, a write and the series and history routes over its Repo; `tasks api` also runs it over every Repo one second past each local midnight. It makes one commit a Repo as `task server` (`write.Server`), the subject its phrases joined by `, `. A Repo refusing writes is passed over and stays flagged, and the call goes ahead.
- **The pass wakes and repeats.** A Deferred leaf whose `until:` is today or earlier moves to Backlog, `until:` and `reason:` cleared (`wake ^id to Backlog`). An ended Task still carrying `series:` gets its next Occurrence above the ended siblings: a copy of it and its Subtasks under fresh ids, every one Backlog, `created:` today, without `ended`, `reason` or `until`, blockers inside the copy remapped, `deadline:` the first rule date after both today and the ended one's Deadline, and the rule moved onto it (`next ^new after ^old`), along with every rule inside it, so a Series inside an ended Series repeats only with it. Missed dates do not pile up and an early finish does not repeat its date. A hand-ticked `[x]` counts as ended the way a `move` does. A rule that has run out is taken off (`end the series of ^id`); one that does not parse is left alone.
- **The clock is a seam.** The pass reads today from `cli.now` and `api.Options.Now`, and the midnight wait from `Options.After`; nil is the real clock. Other writes stamp `created:` and `ended:` from the real one.
- **The client's files are served under `/api/`'s feet, not over them.** The fallback answers any path with `index.html`; `/api/` is registered ahead of it, with or without `-web`, so a route this package does not serve is `400` with a sentence rather than the client at `200`. One `http.Dir` both decides whether a path names a file and serves it.
- **`GET /api/files` lists one directory under the listener's home and opens nothing.** `within` judges a path on how it is spelled and then on where it lands, so a link out of the root is refused the way `..` is. Everything outside gets one sentence, there or not. `Options.Browse` is a test seam, not an operator knob.
- **`tasks api` has no authentication, deliberately, and is meant for the LAN.** Changing that is what ADR 0003's first re-check trigger covers. `:8080` is a wildcard bind, so the host's interfaces decide its reach.
- **Two artifacts are placed on the deploy host, and nothing enforces they match.** The binary `scripts/package tasks` builds goes to `~/.local/bin/tasks`, and `apps/web/dist/` goes to `~/.local/share/tasks/web/`, which the unit's `-web` names.
- **Dates are host-local.** `board.Today` is the host's local date, served as `today` so a surface marks a Deadline today or Overdue against the host rather than the browser; a write or the pass uses `time.Local` the same way.
- **Bare `tasks` is usage, exit 2.** `cli.verbs` is the one list of verbs; the dispatch and the usage sentence are both written from it.
- **The Broker routes write nothing.** `POST /api/capture {text, repo?, task?}` answers a dump as `write.New`'s fields plus `repo`, the Repo it guessed or `""`; naming a `repo` and `task` amends that Task, so the Broker is handed it as it stands, answers it whole, and `repo` is the Task's own (`404` for a Task or Repo not there); the attributes come back as said for the form to correct, and a Repo or Tag is one offered or dropped. `POST /api/ask?<narrowing> {question}` answers `{answer}` about the Tasks that narrowing reads. `POST /api/breakdown {repo, task, answers}` answers `{questions?, proposals}`, each proposal with what the store would refuse dropped and one without a title dropped whole; a Broker answering neither is `500`. The Broker is never an Actor.
- **`tasks capture <words>` writes what the Broker read to the calling Repo or `-repo`, never the Repo it guessed.** A value the store would refuse is dropped rather than refused, since nobody is left to ask; no title is exit 1. `-dry` prints the read and writes nothing.
- **The AI is an outbound HTTP call, never embedded inference.** `TASKS_AI_URL` and `TASKS_AI_MODEL` point it elsewhere; a 429 is the broker's memory budget and is reported as a wait.
- **A rule is written the way it is said, and `schedule.Parse` is the only reader of one.** `String` writes every form back exactly as `Parse` reads it.

## Work Guidance

- Tests first, at the seams: `taskfile` table tests of text to Tasks and problems plus the write-back round trip; a temp root of Repo folders driven through `cli.Run`, with real git and a bare remote for the writes; the routes under `httptest`.
- A write test gives its home a `.gitconfig` with a user and sets `GIT_CONFIG_NOSYSTEM=1`, so commits never depend on the machine's git config.
- A test owns its home: set `HOME` and `XDG_CONFIG_HOME` to a temp directory so discovery never reads the real `~/code`.
- The broker is shared and its chat model is large: a 429 saying `scheduler_busy` means the GPU budget is spoken for. Tests stand a broker in with `httptest` and never reach the LAN.
- The exported vocabulary is `GLOSSARY.md`'s: Repo, Task, Subtask, State, Tag, Blocked, Series, Occurrence, Actor.
